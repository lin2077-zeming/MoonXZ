# moonbit-acceptance-review

一个用于 **MoonBit 项目验收级自查** 的 skill，面向比赛提交与最终验收。

## 为什么需要它

普通的提交前自查走一遍标准清单，每条确认"存在对应工件"：README 存在、CI 存在、
测试存在、已发布。这回答的是**有没有**，而验收方判断的是**是不是真的**。

两者差距可以很大。这个 skill 来自一个真实失败案例：一个 XZ/LZMA 库在清单上全绿
——38 个测试四后端通过、CI 三平台绿、已发布、许可证齐全、文档完善——但验收方用
Python `lzma` 生成的 128 KiB 流让它解码失败，并在源码**行号级**定位了错误。

原因是**所有测试数据都是它自己生成的**。自己的编码器测自己的解码器，只能证明
两者共享同一个误解。同类问题在那个项目里共有四处，共同结构是：

> **文档/测试相信的东西** 与 **代码实际做到的事** 之间的落差。

## 内容

| 文件 | 作用 |
| --- | --- |
| `SKILL.md` | 完整方法说明。核心是"声明对账"与"跨实现验证"两节。 |
| `acceptance_audit.py` | 把可机械化的检查做成脚本。**项目无关**，项目差异由配置提供。 |
| `acceptance_audit.example.json` | 配置样例，逐项带注释说明。 |

## 安装与使用

```bash
# 1. 作为 skill 安装（放到你的 agent 的 skills 目录）
cp -r moonbit-acceptance-review ~/.agents/skills/

# 2. 在项目里跑机械检查
cp acceptance_audit.example.json <你的仓库>/acceptance_audit.json
#    编辑该文件，填上你的模块名、版本声明位置、外部参照实现的命令
python3 acceptance_audit.py <你的仓库>
```

脚本输出 `PASS` / `FAIL` / `UNVERIFIED` 三种状态，**`UNVERIFIED` 不是通过**：
它表示某项检查没跑起来（通常是配置缺项），脚本会在结尾再次提醒。

## 设计原则

1. **报告 UNVERIFIED，绝不假设通过。** 跑不起来的检查不等于没问题。
2. **不把"文档写了"当作功能存在的证据。** 必须定位到实现与覆盖它的测试。
3. **对照单一真相源**，而不是相信多处手写的副本。版本号、测试数量必须唯一。
4. **也查反向漂移**：文档说"不做"而代码已经实现了，同样会被判"完成度不覆盖承诺"。
5. **脚本自己必须被验证过会失败。** 一条永远通过的检查比没有检查更糟。

第 5 条是实践经验：这个脚本的每个检查都做过**差分验证**——故意制造它该发现的
问题，确认它确实 `FAIL`，再还原。例如把负向漂移检查指向一条真实存在的声明，
它如期报 `FAIL`，说明检查真的在工作而不是恒真。

## 项目无关的部分与需要适配的部分

**脚本已覆盖（无需配置）**：工具链版本、版本号一致性、测试数量一致性、
仓库卫生（构建产物被跟踪、许可证、CI、第三方说明）、生成接口是否跟踪且与源码一致、
四条严格命令。

**需要你提供适配脚本（配置里指定）**：

| 配置项 | 要证明什么 |
| --- | --- |
| `external_interop` | 用**外部参照实现**产生的数据测你的解码，并用外部实现验证你的输出 |
| `boundary_cases` | 按**字段宽度**取的边界值（不是 1/100/1000 这类习惯值） |
| `empty_input_check` | 每个入口都能往返空输入 |
| `fuzz` | 畸形输入只产生明确报错，不 panic |

## 已知边界

- 有效代码行数、性能亮点、生态价值这类判断**无法机械化**，仍属人工判断。
- 脚本不是验收方程序。它只是把验收的**可见标准**机械化，减少遗忘与漂移。
- 官方材料里**没有**公开的验收程序或验收 skill。本 skill 的方法来自公开的
  Acceptance Review Checks、官方 CI 模板，与一个真实失败案例的反推。
