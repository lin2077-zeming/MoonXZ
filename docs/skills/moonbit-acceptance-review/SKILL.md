# MoonBit 验收级审查

## 这个 skill 解决什么问题

普通的提交前自查走一遍标准清单，每条确认"存在对应工件"：README 存在、CI 存在、
测试存在、已发布。这回答的是**有没有**。

验收方判断的是**是不是真的**。两者的差距可以很大：一个项目可以在清单上全绿，
同时存在一个让合法数据解码失败的缺陷。

真实案例（MoonXZ，XZ/LZMA 库，第一次验收未通过）：38 个测试在四个后端全绿、
CI 三平台绿、已发布到 mooncakes、许可证齐全、文档完善。而验收方用 Python `lzma`
生成的 128 KiB 流让它解码失败，并在 `lzma2.mbt` 的**行号级**定位了进位错误。

原因不复杂：**所有测试数据都是它自己生成的**。自己的编码器测自己的解码器，只能
证明两者共享同一个误解。同类问题还有三处，它们有一个共同结构：

> **文档/测试相信的东西** 与 **代码实际做到的事** 之间的落差。

所以这个 skill 的核心不是"再列一遍清单"，而是**对账**：把声明、代码、测试、
外部参照实现四者的说法互相核对，任何一处不一致都是发现。

## 使用前提

先确认项目形态，本 skill 的多数步骤对形态无关，少数需要适配：

```bash
moon version --all                 # 工具链版本，单独报告
git ls-files | head -50            # 仓库结构
cat moon.mod                       # 模块名、版本、依赖
moon check --deny-warn --target all
moon test --deny-warn --target all
moon fmt --check
moon bundle --all
```

如果 `moon check` 或 `moon test` 本身就不过，先停下来解决这个——它属于硬性门槛，
后面所有讨论都没有意义。

**工具链版本必须单独报告。** 编译器换代会造成看起来像代码缺陷的失败。真实案例：
`moonc` 0.10.15 开始在 `fmt` 中把 `Int` 改写为 `Int32`，于是
`moon fmt --check` 在整个代码库上失败，`Int` → `Int32` 的全库 diff 看起来像有人
手误改了代码。判断依据是 `moon version --all` 的输出，而不是 diff 的外观。

## 第一部分：硬性门槛

任一不满足即**不建议提交**，不要用"其他方面很好"折抵。

### 1. 合法且可构建的 MoonBit 项目

- `moon check --deny-warn --target all` 通过
- `moon test --deny-warn --target all` 通过
- `moon fmt --check` 通过
- `moon bundle --all` 通过（如果项目声称可发布）

### 2. 已发布到 mooncakes.io，且版本自洽

用模块名查询真实发布状态，不要以"我执行过 publish"为依据：

```bash
# 网页可读的发布状态
# https://mooncakes.io/docs/<owner>/<module>
# 或查询 API
curl -s https://mooncakes.io/api-new/v0/modules/<owner>/<module>
```

必须核对：`latest_version` 与 `moon.mod` 的 `version` 是否一致；`build_status`
是否为 `success`；是否 `yanked`。

**把已发布的源码下载下来重新检查，而不是只检查本地工作区。** 二者可能不同：

```bash
# 在一个全新工程里拉取发布产物
mkdir /tmp/consumer && cd /tmp/consumer
moon new consumer --user reviewer --name consumer
moon add <owner>/<module>
# 已发布源码落在 .mooncakes/<owner>/<module>/
cd .mooncakes/<owner>/<module> && moon check --deny-warn --target all
```

真实案例：发布产物里 README 还是上一版内容（mooncakes 在**发布时**抓取 README
快照，已发布版本无法修改），于是页面上"版本 0.4.2、说明里写当前版本 0.4.1"。

### 3. 许可证

- 根目录有 OSI 认可许可证文件
- 参考/移植他人项目：列出原项目名、链接、许可证、参考范围
- 存在上游许可证原文（如 `LICENSES/`）
- 依赖的许可证也被记录

### 4. 仓库卫生

```bash
git ls-files | grep -E '^(_build/|target/|\.mooncakes/)'   # 应为空
git status --porcelain                                      # 工作区应干净
git ls-files | grep -i license                               # 应有
git ls-files | grep '^\.github/workflows/'                   # 应有
```

### 5. 提交历史与归属

- 主要贡献者、仓库所有者、申请人是否为同一人（不一致必须有说明）
- 提交数是否足够、信息是否清晰、是否集中在参赛周期
- **不要建议空提交、重复提交或机械拆分来凑数量**

### 6. 能真正运行

README 或仓库提供的启动命令必须真的跑起来，并核对输出与文档一致：

```bash
moon run cmd/main -- <文档里的示例参数>
```

## 第二部分：声明对账（本 skill 的核心）

**这一步是清单式自查与验收级审查的分界线。** 不要跳过。

### 做法

从申报书、README、`CHANGELOG`、文档注释中**逐句抽取原子声明**，每条独立判定。
一条声明包含多个能力就拆开。对每条记录：

```text
声明原文 | 声明位置(文件:行) | 实现位置(文件:行) | 验证方式(命令或测试名) | 结论
```

### 铁律

1. **禁止用"文档写了"作为实现存在的证据。** 必须定位到实现代码与覆盖它的测试。
   找不到就是 `未实现` 或 `未覆盖`，不是"应该没问题"。
2. **禁止用"测试通过"作为能力存在的证据。** 测试通过只说明测试断言的东西成立；
   要看断言是否覆盖了该声明声称的场景。
3. 结论只有三种：`已兑现`、`未兑现`、`无法判定`。**没有"大概"**。
   `无法判定` 要写明缺什么信息。

### 能力声明的常见形态（都要查）

- 功能列表 / 特性表
- "支持 X 格式 / 可与 Y 互通"
- 使用场景段落里的承诺（最容易被忽略）
- 性能数字
- 测试数量、覆盖率描述
- API 清单
- "已交付"与"明确不做"两个清单

### 场景段落是重点

使用场景往往写成散文，读起来像愿景，实际是**可验证的承诺**。

真实案例：申报书写使用场景"备份与日志归档 CLI：……通过流式 Reader/Writer
按 block 处理，**避免一次性载入全部内容**"。验收反馈第三条正是
"块级 API 存在，但 Reader 及文件 CLI 仍全量读入，**未兑现内存场景**"。

判据不是"有没有流式 API"，而是**端到端路径上内存是否真的有界**。有 API 不等于
调用方用了它。

## 第三部分：反向漂移（做了却声明不做）

**只查"声明了没做"会漏掉一半。** 文档会向两个方向漂移。

申报书写作时的"明确不做"是**当时**的事实。之后实现了，这句话就变成假的。
验收方按"完成度必须实质覆盖申报书的核心承诺"对账时，看到的是一份
**自我否认了已完成工作**的文档——这同样会被判"完成度不覆盖承诺"。

真实案例：申报书写"不提供逐字节增量接口，流式 API 以 block 为单位"，
而项目后来已经实现了支持逐字节喂入的流式解码器。

做法：**对每条"不做/不支持/未实现"的声明，去代码里找相反证据。**

```bash
# 对该声明提到的能力，在源码与接口里搜索
moon info && grep -i '<能力关键词>' */pkg.generated.mbti
grep -rn '<能力关键词>' src/ lib/
```

如果找到了，这条声明要么删掉，要么改写成真实边界。

## 第四部分：指标与常量的单一真相源

文档里的数字会腐烂，且**同一个错误会重复犯**。

### 必须机械核对的项目

| 项目 | 真相源 | 需要核对的地方 |
| --- | --- | --- |
| 版本号 | `moon.mod` 的 `version` | README、CLI banner、CHANGELOG、申报书、已发布产物 |
| 测试数量 | `moon test` 的 `Total tests` | README、申报书、进度文档 |
| 模块名 | `moon.mod` 的 `name` | README 的 `moon add` 示例 |
| 依赖版本 | `moon.mod` 的 `import` | 第三方说明文档 |
| 性能数字 | 基准脚本 | README 引用的表格 |

### 硬编码副本必须消除

真实案例：CLI banner 把版本号**手写**在第二个地方，于是漂移了**两次**——
先打印 `0.4.0` 而模块是 `0.4.2`，修好后又打印 `0.4.2` 而模块是 `0.4.4`。
两次都是靠人偶然运行 CLI 才发现的。

**正确修法不是"再改一次"，而是消灭副本：**

```moonbit
///|
const CLI_VERSION : String = "0.4.4"

///|
fn usage() -> Unit {
  println("MoonXZ \{CLI_VERSION}")
```

然后让某个检查覆盖"常量 == `moon.mod` 的 version"。

> 注意：MoonBit 的 main 包不适合放测试来读文件（包外的 `@fs` 相对路径依赖
> `moon test` 的工作目录，且 main 包的内部符号对测试不可见）。把这类跨文件对账
> 放在**脚本**里，不要勉强写成单元测试。

**如果你的项目有 CI，把数字对账放进 CI**，否则它一定会在某次改版本时再次腐烂。

## 第五部分：跨实现验证（不可省略）

### 为什么必要

**用自己的实现生成测试数据，无法证明互通性。**

如果编码器与解码器对格式规范有同一个误解，自产数据完全自洽——编码按误解写、
解码按误解读，测试全绿。缺陷只在遇到**别人的实现**产生的数据时暴露。

真实案例：所有 fixture 都是 MoonXZ 自己生成的，而它的编码器把块上限保守地压
在 64 KiB，于是那个 18 位长度字段的进位路径**在自产数据上永远走不到**。
验收方用 Python `lzma` 生成 128 KiB 流，一次就撞上了。

### 做法

**双向**都要做，单向不够：

```text
1. 外部实现生成 → 本项目解码 → 与原文逐字节比较（这是验收方的方向）
2. 本项目编码 → 外部实现解码 → 与原文逐字节比较（证明输出合法）
```

**必须包含"外部实现的合法输出"作为输入**，而不只是"本项目自己的输出"。

### 找参照实现

| 领域 | 参照实现 |
| --- | --- |
| 通用压缩/归档 | Python 标准库（`zlib`/`gzip`/`bz2`/`lzma`/`tarfile`/`zipfile`）、`xz-utils`、`zstd` |
| 序列化/格式解析 | Python 标准库对应模块、`jq`、`xmllint`、语言原生解析器 |
| 加密/摘要 | Python `hashlib`/`hmac`、`openssl` |
| 数值/编码 | Python `struct`/`base64`/`codecs` |
| 协议 | 官方测试向量、参考实现的测试套件 |

如果没有独立实现可比，**在报告里明确写出"无外部参照，互通性未验证"**，
不要用"我们自己往返测试通过"替代。

### 生成数据要覆盖形态，不是只覆盖一种

真实案例：初版 filter 测试只用"单一重复模式 + 单一长度"，缺陷因此躲过。补上
"多长度 × 多内容形态"矩阵后立刻暴露。

数据形态至少覆盖：全零、重复小周期、随机不可压缩、半可压缩、真实样本、
以及该格式的**典型结构**（如二进制中的可执行文件分支指令、文本、结构化数据）。

## 第六部分：边界与算术路径

### 按字段宽度取边界，不要按习惯取

真实案例：出错的长度字段是 **18 位**，存储为"控制字节低 5 位 + 16 位低位"，
编码的是 `长度 - 1`。失败条件是**低位为 `0xFFFF`**，即长度不是 65536 的整数倍。
只测 64 KiB 恰好落在临界点上而不触发——所以"有边界测试"并不足够，**要按字段
结构取**。

对每个从输入读取的数值字段：

| 字段形态 | 必测取值 |
| --- | --- |
| 跨字节拼接 | 低位全 1（触发进位）、低位全 0、恰好跨边界 |
| 尺寸字段 | 0、1、字段上限、上限 ±1、上限 × k |
| 长度前缀 | 0、1、等于缓冲上限、超过缓冲上限 |
| 变长整数 | 最短编码、最长编码、恰好 64 位、溢出 64 位 |
| 偏移/距离 | 0、1、等于窗口大小、超过窗口大小 |
| 声明大小 | 与实际不符（偏大、偏小） |

### 空输入与退化输入

**每个入口都要测空输入。** 真实案例：`.lzma` 编码直接拒绝空输入，使这个入口
成为唯一不能编码空值的入口，验收方专门列了出来。

退化输入清单：空、1 字节、恰好等于内部块/缓冲上限、上限 ±1、
长度是内部周期长度的整数倍。

### 算术路径必须单独测

畸形输入测试容易只覆盖**结构性**损坏（截断、单字节变异、随机垃圾），
而漏掉**长度字段极大值**这一专门的算术路径。

真实案例：边界检查写作 `pos + length > data.length()`，而 `length` 来自输入。
二者相加可**溢出成负数**从而通过检查，随后按该长度读取就越界。28 字节的畸形输入
即可触发崩溃。

```text
错误：if pos + length > data.length()     // 加法可溢出
正确：if length > remaining                // 每一项都有界
```

审计所有"来自输入的数值参与算术"的位置，检查：
- 加法/乘法是否会溢出
- 边界检查本身是否可能被溢出绕过
- 声明的工作量是否有上限（防止"声明超大输出"造成内存膨胀）

## 第七部分：畸形输入健壮性

**要求**：任何输入都只能产生"明确报错"或"正确结果"，**不得 panic、trap、
崩溃、静默产出错误数据**。

### 必做三类

1. **截断**：对一份合法数据，逐一取每一字节前缀，每个前缀都不得解出原数据
2. **变异**：单字节全量变异（256 种取值 × 每个位置），不得 panic
3. **伪随机垃圾**：完全没有合法结构的输入，与变异测试互补

### 加上算术路径

第 2 类之外的专门构造：极大长度字段、能造成加和溢出的组合、
声称的限额附近的取值。

**声称的限额必须在限额处失败，而不是崩溃。** 真实案例：文档说支持输出大小限制，
而畸形输入在"输出限额 1024"下依然 trap。

### 命令示例

```bash
# 提供一个可复现的模糊测试脚本，并纳入报告
python scripts/fuzz_cli.py . 200
```

不要把"我手工试了几个"当作健壮性证据。

## 第八部分：后端矩阵与工具链

### 四目标一致

```bash
moon check --deny-warn --target all
moon test --deny-warn --target all
```

`wasm` / `wasm-gc` / `js` / `native` 必须一致通过。声称"可运行于四个目标"就必须
在四个目标上验证——只在 `native` 通过不能支持该声明。

### 工具链适配

- 报告 `moon version --all`，与项目声明的**最低版本**对照
- 若 CI 安装 `latest`，注意 CI 可能与本地不同版本：**这会造成看起来像代码缺陷的
  失败**。在 CI 中加入版本校验步骤，让未验证的编译器版本明确失败
- 编译器换代（如 `Int` → `Int32` 的格式化风格）属于**适配工作**，
  在 CHANGELOG 中记录

## 第九部分：官方 CI 模板与接口检查

官方推荐的 CI 参考（`moonbit-community/.github` 的 workflow-templates）核心步骤：

```bash
moon check --deny-warn --target all
moon test --target all
moon fmt && git diff --exit-code
moon info && git diff --exit-code
```

**注意 `moon info` 这一项容易被做成空操作。** `moon info` 生成的
`pkg.generated.mbti` 默认不被跟踪，而 `git diff` **不看未跟踪文件**，
于是 `git diff --exit-code` 永远通过、检查毫无作用。

要让它真正生效，必须把接口文件提交进仓库：

```bash
moon info
git add -A -- '*pkg.generated.mbti'
git commit -m "chore: track the generated interface"
```

这样公开 API 的意外变更会变成**可审查的 diff**，而不是悄悄发布。

接口文件本身也是评审价值：它以一行一个符号的形式列出全部公开 API，
既是文档也是契约。

## 第十部分：加分项（决定竞争力，不决定是否通过）

- `check --deny-warn` / `test --deny-warn` / `fmt --check` / `moon info` 接口无意外差异
- CI 覆盖 check / build / test 三流程，且三平台（Linux / macOS / Windows）
- 有效源码规模（4k 行量级是参考，不是硬指标）
- 文档、示例、基准齐备，且**性能数字能由脚本重新生成**而非被信任
- 架构清晰、注释与文档充分、无明显潜在风险
- README 能让陌生人在无额外信息下跑起来

## 报告格式

```markdown
## 总体判断
（能否通过验收；阻塞项数量）

## 硬性门槛
（逐条：通过 / 不通过 + 证据命令）

## 声明对账表
| 声明原文 | 声明位置 | 实现位置 | 验证方式 | 结论 |

## 反向漂移
（代码已实现但文档称不做的地方）

## 需要处理的问题
（按严重性排序，每条附可复现命令或 文件:行）

## 需要进一步确认的问题
（无法本地验证的，列为待确认，不得判定）

## 建议改进
（加分项方向）

## 已检查的证据
（实际执行过的命令与结果摘要）

## 工具链
（moon version --all 输出，单独报告）
```

### 报告纪律

- **区分事实、推断、无法判定的规则解释**，不要把推断写成结论
- 每条结论附**可复现命令**或**文件:行号**
- 无法本地验证的列为"待确认"
- 发现个人敏感信息时，只报告风险与位置，**不要复述内容**

## 完整案例：XZ 解码库的四个发现

用于校准判据。这个项目在清单式自查上全绿，验收未通过。四个发现全部属于
"声明与实现的落差"：

| 发现 | 声明 | 实际 | 为什么自查漏了 |
| --- | --- | --- | --- |
| 合法 128 KiB Python XZ 解码失败 | README 称可与 Python `lzma`/`xz-utils` 互通 | 18 位长度字段进位错误，非 65536 倍数即算错 | **所有 fixture 都是自产的**，该路径走不到 |
| 28 字节畸形输入崩溃 | README 称对损坏输入健壮 | 长度校验 `pos+length` 溢出，越界 | 健壮性测试只覆盖结构性损坏，漏了长度极大值 |
| Reader/CLI 全量读入 | 申报书承诺"按 block 处理，避免一次性载入" | CLI 全量读入 | 只确认"有流式 API"，没验证端到端内存 |
| `.lzma` 空输入不支持 | — | 编码器直接拒绝空输入 | 没测空输入 |

外加一处**反向漂移**：申报书写"不提供逐字节增量接口"，而项目已实现该接口。

**从这四条能推出的判据**：

1. 互通性声明必须用**外部实现的数据**验证
2. 边界要**按字段宽度**取，不是按习惯取
3. **场景段落里的承诺**要端到端验证，不能只看有没有对应 API
4. **空输入**每个入口都要测
5. "不做"清单要**反向核对**

## 反模式（不要做这些）

- ❌ 用"README 里写了"当作功能存在的证据
- ❌ 用"测试通过"当作能力存在的证据，而不看断言覆盖了什么
- ❌ 只用自己的实现生成的测试数据验证互通性
- ❌ 只查"声明了没做"，不查"做了却声明不做"
- ❌ 边界测试只取整数习惯值（1、100、1000），不按字段宽度取
- ❌ 版本号、测试数量在多处手写副本
- ❌ 声称四目标支持但只在 `native` 上验证
- ❌ 把 `moon info && git diff` 做成空操作（接口文件未跟踪）
- ❌ 把无法验证的东西写成结论，而不是标为"待确认"
- ❌ 建议空提交/机械拆分来凑提交数量
