## 二、从四个缺陷反推验收方做了什么

验收反馈原文（四个问题）：

1. 申报"LZMA2压缩块解码"是主要用途核心；`lib/lzma2.mbt:39-40` 长度合并进位错误，
   合法 128KiB/256KiB/1MiB Python XZ 解码失败。原 CLI 及发布 0.4.2 四目标重现。
2. 28 字节异常输入又使 `lib/util.mbt:82` 整数溢出、`:87` 越界，输出限额 1024 仍 trap/崩溃。
3. 不是基础设施异常。
4. 块级 API 存在，但 Reader 及文件 CLI 仍全量读入，未兑现内存场景；`.lzma` 空输入编码不支持。

从这些措辞可以**确定**验收方执行了以下动作（都是事实层面的观察，不是猜测）：

| 观察 | 证据 |
| --- | --- |
| 阅读了申报书，并把它当验收依据 | 开头即引"申报 LZMA2压缩块解码是主要用途核心" |
| 读了源码到**行号级** | 两处精确到 `lzma2.mbt:39-40`、`util.mbt:82`/`:87` |
| 用**外部工具生成的数据**做输入 | "合法 128KiB/256KiB/1MiB Python XZ" |
| 在**四个目标**上都复现 | "原 CLI 及发布 0.4.2 四目标重现" |
| 构造并测试**畸形输入** | "28 字节异常输入"、"输出限额 1024 仍 trap" |
| 追查**根因**而不止现象 | "长度合并进位错误"是对代码语义的判断 |
| 交叉验证是否环境问题 | 专门说明"不是基础设施异常" |
| 读 README/申报书的**能力声明**并逐条对账 | 内存场景、`.lzma` 空输入两项直接对应文档承诺 |
| 用自己发布的版本验证 | "发布 0.4.2 四目标重现" |

### 推断（标注为推断）

验收方大概率执行了类似以下的流程。依据是上述观察能否被这套流程解释：

```text
1. 读申报书与 README，抽出可验证的能力声明
2. 核对每项声明在代码中是否有对应实现
3. 对每项能力，用外部参照实现（python lzma / xz-utils）构造输入，而非只用项目自产数据
4. 沿边界取值：chunk 大小边界、空输入、超大声明、畸形长度字段
5. 在四个后端全部执行
6. 对失败项追踪到源码行，判断根因
7. 排除环境因素后，把问题定性为项目缺陷
```

**与我们失败的对应关系：**

| 验收方动作 | 命中的缺陷 |
| --- | --- |
| 用外部实现的数据（步骤 3） | 缺陷 1：进位错误只在外部产生的 ≥64KiB 压缩块上触发 |
| 沿边界取值（步骤 4） | 缺陷 1（非 65536 倍数）、缺陷 4（空输入） |
| 构造畸形输入（步骤 4） | 缺陷 2：长度字段溢出导致越界 |
| 声明对账（步骤 1–2） | 缺陷 4b：README 承诺流式，实现不支持 |

## 三、根因分析：为什么自查没查出来

### 3.1 四个缺陷的**共同结构**

> 每一个都是"**文档/测试相信的东西**"与"**代码实际做到的事**"之间的落差。

- 缺陷 1：README 说可与 `xz-utils`/Python 数据互通，**但所有测试数据都是 MoonXZ
  自己生成的**。自己的编码器把块上限压在 64 KiB，于是那条进位路径在自产数据上
  **永远走不到**。测试全绿，能力声明是假的。
- 缺陷 4b：申报书写作时"不提供逐字节增量接口"**是真的**；后来加了
  `XzStreamDecoder`，这句话**变成假的**，但没人回头改。验收方按"完成度必须实质
  覆盖申报书承诺"对账时，看到的是一份**自我否认了已完成工作**的文档。
- 缺陷 3：申报书承诺 CLI "按 block 处理，避免一次性载入全部内容"，实际 CLI
  全量读入。**同一句话，文档承诺 vs 实现行为不一致。**
- 缺陷 2：`README`/测试声称对损坏输入健壮，但健壮性测试只覆盖了**结构性损坏**
  （截断、单字节变异、伪随机垃圾），没覆盖**长度字段极大值**这一专门的算术路径。

### 3.2 自查失败的方法论原因

我先前写的《验收自查清单》逐条走过 9 条验收标准，每条都确认"存在对应工件"：
README 存在、CI 存在、测试存在、已发布。**这是清单式验证**（checklist
verification），它回答"有没有"，而验收方回答的是"**是不是真的**"。

结果就是：清单全绿，而代码里有一个能让合法数据解码失败的错误。

三条具体教训：

1. **自产数据不能验证互通性。** 用自己的编码器生成 fixture，只能证明
   "编码器与解码器共享同一个误解"。跨实现验证必须引入**外部实现产生的数据**。
2. **边界不是"有测试"就够，要按字段宽度取。** 18 位字段拆成 5+16 两次读取，
   失败点是低位为 `0xFFFF`（即长度非 65536 倍数）。只测 64 KiB 正好落在这个
   临界点上而不触发。
3. **文档与代码会双向漂移。** 不只"文档承诺了代码没做"，也包括"代码做了而文档
   还写着不做"。后者同样会被判"完成度不覆盖承诺"。

## 四、反推出的验收 skill（重建版）

以下是把上述方法固化成可复用流程的结果。它对应一个"验收审查" skill 应当做的事。

```markdown
---
name: moonbit-acceptance-review
description: 对 MoonBit 比赛项目做验收级审查。当用户要求验收自查、审核、判断能否通过验收时使用。
---

# 验收级审查

清单式自查（确认工件存在）不足以通过验收。以下每一步都必须产出**可执行证据**，
不能以"文件存在"作为通过依据。

## 硬性门槛（任一不满足即判不通过）

1. 合法 MoonBit 项目；`moon check --deny-warn` 与 `moon test --deny-warn` 通过
2. 已发布到 mooncakes.io，且 `moon.mod` 的 `version` 与线上一致
3. 根目录有 OSI 认可许可证；第三方来源与许可证有说明
4. 仓库无构建产物/缓存被跟踪
5. 提交历史合理，主要贡献者 = 仓库所有者 = 申请人
6. `moon run` 或 README 中的启动方式真实可跑
7. 运行时无严重正确性或性能问题
8. 申报书与 README 的**每一项能力声明**在代码中有对应实现

## 声明对账（本 skill 的核心）

对申报书与 README 逐句抽取原子声明，逐条判定。**不预设任何声明为真。**

对每条声明记录：`声明原文 | 声明位置 | 对应实现位置 | 验证方式 | 结论`

必须主动查找两类反向漂移：
- 声明了但代码未实现（虚报）
- 代码已实现但文档声明为不做（漏报，同样会被判"完成度不覆盖承诺"）

**禁止**用"文档写了"作为实现存在的证据；必须定位到实现与测试。

## 跨实现验证（不可省略）

- 用 `python3 -m lzma`、`xz-utils`、或该格式的权威实现**生成**输入，交给本项目解码
- 反向：本项目编码的输出交给权威实现解码
- **本项目的编码器不能只用自己的输出做测试**：编码器与解码器共享的误解无法被自产数据发现
- 测试数据必须来自外部，或明确标注为自产并说明覆盖不到哪些路径

## 边界取值（按字段宽度，而非按习惯）

对每个从流中读取的数值字段，按其**存储宽度**取边界：

- 跨字节拼接的字段：低位取全 `1`（触发进位）、全 `0`、以及恰好跨边界的值
- 尺寸字段：0、1、字段上限、上限 ±1、以及"字段上限 × k"
- 空输入、单字节、恰好等于内部缓冲/块上限的输入
- 声明长度极大值（接近 `Int` 上限）、负值、能造成加和溢出的组合

## 畸形输入健壮性

- 截断：每一字节前缀都不得解出原数据
- 变异：单字节/单 bit 翻转不得 panic
- **算术路径**：极大/极小长度字段组合，验证边界检查本身不溢出
- 声称的限额（如输出上限）必须在**限额处**失败，而不是崩溃

## 后端矩阵

`moon check --deny-warn --target all` 与 `moon test --deny-warn --target all`。
四目标（wasm / wasm-gc / js / native）必须一致。

## 加分项（决定竞争力）

- `moon fmt --check`；`moon info` 后审查接口差异（官方 CI 模板含此项）
- CI 覆盖 check / build / test 三流程，三平台
- 有效 MoonBit 源码规模接近或超过 4k LOC
- 文档、示例、基准、性能数据齐备且**可复现**（数字须能由脚本重新生成）

## 报告要求

- 区分事实、推断、无法本地验证的规则解释
- 每条结论附可复现命令或文件:行号
- 不能本地验证的列为"待确认"，不得直接判定
```

## 五、我们据此补上的机制

光改文档不够——文档还会再漂移。所以把能机械化的部分做成了脚本。

### 可复用的通用 skill

本文第四节的重建版已抽成**项目无关**的独立 skill，供其他 MoonBit 项目参考：

```text
docs/skills/moonbit-acceptance-review/
├── SKILL.md                       完整方法（声明对账、跨实现验证、边界取法…）
├── acceptance_audit.py            通用审计脚本，项目差异由配置提供
├── acceptance_audit.example.json  配置样例（逐项带注释）
└── README.md                      安装与设计原则
```

通用脚本把项目相关的部分（用哪个外部实现、哪些边界值、空输入与畸形输入怎么测）
外置为 `acceptance_audit.json` 中的四个适配项，脚本本身不含任何 XZ 相关逻辑。
在本仓库上实测：**26 项检查，25 ok / 0 failed / 1 unverified**（未通过项是
"工作区未提交"，提交后即消失）。

其中每个检查都做过**差分验证**——故意制造它该发现的问题，确认它确实 `FAIL`，
再还原。例如把负向漂移检查指向一条真实存在的申报书声明，它如期报
`FAIL drift: '明确不做' ... still claimed but lib/streaming.mbt matches ...`，
说明该检查真的在工作而不是恒真。**一条永远通过的检查比没有检查更糟。**

### `scripts/self_audit.py`（本仓库专用）

20 项检查，全部产出可执行证据；**不能机械验证的列为 UNVERIFIED 而不是默认为真**。
本次运行结果：**20 ok / 0 failed / 0 unverified**。

| 类别 | 检查内容 |
| --- | --- |
| 工具链 | `moonc >= 0.10.14` |
| 版本一致性 | `moon.mod` / README / `CLI_VERSION` 三处一致，且 banner 由常量插值 |
| 测试数一致性 | 申报书/README/Progress 声称的测试数 == 实测 46 |
| **反向漂移** | 若文档称"不提供 X"，而代码已存在 X，则失败 |
| API 对账 | 文档点名的每个 API 都出现在 `lib/pkg.generated.mbti` |
| 仓库卫生 | 无构建产物被跟踪、有许可证、有 CI、有第三方说明 |
| 严格命令 | `check --deny-warn --target all`、`fmt --check` |
| 空输入 | xz 与 lzma 都必须往返成功 |
| **边界尺寸** | 65535 / 65536 / 65537 / 131072 / 131073 / 262144 / 1048576 全部精确解码 |
| **跨实现** | `scripts/interop.py` 外部 liblzma 双向 |
| 健壮性 | 畸形输入不得 panic |

**这个脚本第一次运行就抓出两处我手工遗漏的漂移**，其中一个是我自己刚修过、
又复发的问题：

- `cmd/main/main.mbt` 的 CLI banner 仍打印 `0.4.2`，而 `moon.mod` 已是 `0.4.4`
  （此前已因 `0.4.0` vs `0.4.2` 修过一次，**同一个错误犯了两次**）
- `Progress.md` 仍写"34 个测试"

这正是清单式自查查不到、而机械对账能抓到的东西。

### 修法的强化

- banner 改为由 `const CLI_VERSION` 插值（`println("MoonXZ \{CLI_VERSION}")`），
  并在 `self_audit.py` 中检查该常量与 `moon.mod` 一致、且 banner 确实使用插值。
  这样"改版本号漏改 banner"会直接被脚本判失败。
- 申报书修掉两处失真：测试数 `34` → `46`；删去"不提供逐字节增量接口"
  （已由 `XzStreamDecoder` 兑现），并把"文件 CLI 不做流式落盘"如实写入
  "明确不做"（原因是 `moonbitlang/x/fs` 无追加接口）。

### 仍未覆盖的部分（诚实记录）

- `scripts/self_audit.py` 不是验收方程序，只是**我们把验收方的可见标准机械化**的结果。
- `moon info` 接口差异审查**尚未加入 CI**。官方模板的
  `moon info && git diff --exit-code` 对本仓库是空操作（`.mbti` 未跟踪，且
  `git diff` 不看未跟踪文件）。要真正生效需改为跟踪 `.mbti` 或用
  `git add -A && git diff --cached --exit-code`。
- 有效代码行数、性能与生态价值等"亮点"类判断无法机械验证，仍属人工判断。
